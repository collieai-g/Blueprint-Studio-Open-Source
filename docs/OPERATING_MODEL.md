# 藍圖的主要運作方式

[返回首頁](../README.md) · [左右協作流程](LEFT_RIGHT_WORKFLOW.md) · [Agent 規格](AGENT_CONTRACT.md) · [安裝](INSTALL.md) · [更新](UPDATE_ROUTE.md)

**左側 Codex 理解要求、使用 Skill 並執行工作；右側藍圖保存資料、呈現操作及結果。專業工作優先由可重用的 Skill 配合目前已有的工具完成。** 影片設計、客服草稿或報告整理，可以先共用這套分工，無須為每個部門再開發一個會自行思考的 AI 服務。

藍圖提供「總覽、工作、AI、資料」四個主要入口，以及檔案、任務、設定、版本和結果的共用底層。使用者在左側說明目標，在右側選擇資料及查看成果。右側不監聽左側私人對話，也不會因為開啟頁面或建立工作就自動喚起 Codex。

## 左右兩側怎樣配合

| 部分 | 負責甚麼 | 交給另一側甚麼 |
| --- | --- | --- |
| 左側 Codex 或相容 AI 客戶端 | 理解使用者要求，讀取選定資料，使用 Skill，操作目前真正可用的工具 | 已整理的內容、實際產生的檔案、引用來源及處理結果 |
| 右側藍圖工作台 | 提供上載、表單、資料選取、工作狀態、版本檢查與結果查看 | 使用者指定的材料、工作要求、偏好及可核對的保存結果 |
| Skill | 定義專業流程、風格、檢查方法及交付格式 | 可重用的處理指引；不自帶模型、帳戶或影片生成能力 |
| 外掛／工具 | 提供瀏覽器控制、影片生成、檔案處理等實際能力 | 真正的操作及產出；依目前客戶端已載入及授權的能力執行 |

支援控制同一個已登入工作台的客戶端，可讓 Codex 直接點擊、填表、上載及保存，再從畫面核對結果。這種方式不需要使用者另寫 API 呼叫或先安裝藍圖 MCP。**瀏覽器控制是否可用，必須檢查目前對話真正提供的工具；右側看得到網站，本身不代表 AI 可以操作它。** 執行環境內另一個測試瀏覽器，也不代表已取得使用者右側分頁的登入與控制權。

藍圖網頁按下「保存」後，仍由現有的已登入後台處理權限、版本和持久儲存。這是產品底層；直接操作畫面省去的是 AI 另外接駁 API 的步驟，並不移除後台資料服務。有已授權的 MCP／工具時，也可直接保存同一份資料；兩條操作路徑共用相同的權限及版本規則。

若目前對話沒有瀏覽器控制，可使用已接通的藍圖工具，或交接 Skill 和工作說明，讓使用者在支援的客戶端繼續。匯出檔案、安裝 Skill、載入外掛及完成工作，是不同的狀態，分別按實際結果回報。

## 專業能力先做成 Skill

新增「影片設計」時，優先準備一份專業流程，加上公司偏好和本次材料。例如品牌語氣、參考畫面、字幕風格及比例屬於設定；這次宣傳的產品、片長及選定照片屬於工作輸入。Codex 把這些內容與可用影片工具配合，完成個人化的成品。

在「AI」的 Skill 工作台準備欄位、選定來源，並將需要的專業推理交給左側 Codex 起草。右側把使用者填寫的指引整理成可複製、下載或保存的交接內容，不會只因上載材料就自行分析並安裝新外掛。可重用的 `SKILL.md` 保存工作方法；單次工作說明保存目標及選定來源。公司材料和私人偏好留在私人工作台或私人交接檔，不加入公開 Skill 範本。Skill 可先由 Codex 根據需求起草，在支援的客戶端依其正式流程安裝；藍圖匯出檔案不會自動把新能力安裝到另一個程式。只有需要新的可執行能力或對外服務時，才另外開發外掛或工具。

[左右協作流程](LEFT_RIGHT_WORKFLOW.md)列出完整影片例子及驗收方式；[個人化影片 Skill 範本](../templates/skills/personal-video/README.md)提供可重用的工作規則。現有獨立 Agent 登記和版本化工作保留，適合需要固定設定快照、來源核對及持久工作狀態的情況，並非使用每一份 Skill 的前置條件。

新安裝不預先建立四位專員。需要網站客服、WhatsApp、電郵或影片設定時，由管理員選擇預設角色或範本新增；已有專員設定、引用及歷史仍保留。保存收藏或新增靈感時，不自動建立截圖與摘要指令；使用者要求整理時才建立相應工作。

藍圖目前沒有背景 AI 執行器。開發範本與[獨立摘要示範](https://github.com/collieai-g/collieai-g-Blueprint-Agent-Summary)用來驗收接駁；既有專員設定、套件登記或「已連接」字樣，也不表示正在運行一個客服或影片服務。

## 日常保存與程式更新

判斷操作是否需要部署，要看現有程式是否已支援，而不是看操作有沒有用到 AI。

| 操作 | 保存位置與流程 | 是否更新程式倉庫及部署 |
| --- | --- | --- |
| 新增今日工作、更新待辦、保存文件、加入收藏、整理報告、修改公司資料 | 使用者或具備控制能力的 AI 操作畫面；亦可用已授權工具。兩者保存到同一私人後台，修改檢查版本，保存後讀回 | 不需要 |
| 修改現有公司或 Agent 設定 | 透過現有畫面或已授權工具保存；既有 Agent 工作保留當時快照 | 不需要 |
| 起草或調整 Skill、準備單次工作說明 | 保存為私人指引或交接檔；依所用客戶端安裝及載入 | 不需要，除非同時修改藍圖原本沒有的功能 |
| 使用既有功能拖動卡片、調整大小或收合 | 保存目前瀏覽器的排版偏好 | 不需要 |
| 登記符合已部署規格的 Agent | 核對固定版本及說明檔，登記到私人後台，再設定及啟用接口 | 通常不需要 |
| 修改版面程式、按鈕邏輯、加入未支援的能力或升級 Blueprint | 整合程式、測試、核對可還原備份，再部署受影響服務 | 需要 |

例如「整理今天的公司報告」是資料工作；「新增原本沒有的報告畫面或運算服務」才可能是程式開發。AI 先使用既有能力，不應把每次保存資料都變成 Git 提交或網站更新。

## 長期維護公司版本

以下以「一二三醫療工作室」作示例，不代表已建立公司倉庫或部署服務。

| 位置 | 負責保存 |
| --- | --- |
| Blueprint 公開倉庫 | 通用程式、接駁規格、開發範本與公開文件 |
| 公司私人 GitHub 倉庫，例如 `123-medical-studio` | 公司使用的完整程式版本、專用修改，以及需要的接駁程式 |
| Skill／Agent 來源位置 | 可重用規則、範本和版本；公開來源只放可公開的內容，私人偏好另存 |
| 私人後台與附件儲存 | 公司文件、工作紀錄、Agent 登記與設定、結果及引用來源 |
| 平台秘密設定與私人維護位置 | 憑證、部署設定、安裝進度與完整備份；不提交 Git |

公司需要長期開發專用功能時，先核對擁有者、名稱及私人可見性，建立或沿用自己的程式倉庫，保留原授權及來源版本。直接使用未修改原版時不強制建立公司倉庫。私人程式倉庫也不作為正式公司資料庫或完整備份的位置。

Blueprint 發布新版後，由使用者要求 Codex 按[更新流程](UPDATE_ROUTE.md)接續：

1. 固定本次上游版本及 commit，取回公司正在維護的版本。
2. 整合新版並保留公司專用功能與 Agent 接駁，處理衝突及執行必要測試。
3. 核對完整可還原備份，將通過測試的程式保存到公司私人倉庫。
4. 明確部署到原有服務，保留網址、登入、資料與附件，再驗證真實寫入及讀回。

上游發版不會自動同步公司倉庫；推送 GitHub 不代表 Sites 或後台已更新。Blueprint 版本、公司程式 commit、Agent 版本與正式部署版本分開記錄，不能只修改版本文字就稱為升級完成。

## 新增及更新客服 Agent

假設首個操作是「根據已選 FAQ 草擬回覆」，由目前 Codex 對話執行：

1. 開發者在獨立倉庫提供符合規格的 `agent.json`，包括規則、設定欄位、操作及共用介面描述，發布可核對的固定 commit。
2. Codex 或管理員核對版本，使用工作台或 MCP 登記該套件，再填寫設定及啟用接口。登記是私人後台的資料操作。
3. 使用者選定可用 FAQ 和客戶問題，建立工作，再在 Codex 要求處理。
4. Codex 讀取指定資料，依規則保存回覆草稿及來源，讀回後由工作台顯示相同結果。

只要已部署的藍圖支援該規格，以上接入通常不需要修改公司倉庫或重新發布 Sites。把檔案複製到公司倉庫、填入 GitHub 網址或顯示「已連接」，都不等於已安裝任意程式或驗證目前對話能執行。

Agent 套件規則更新時，核對並另行登記新版本；舊工作仍使用建立時的快照。一般實例設定則直接保存。Agent 與 Blueprint 各自選定版本，不會因另一方更新就自動切換。

需要自訂程式畫面、新工具或額外服務時，先完成相容接駁，再整合公司程式及部署。若要關閉 Codex 後仍自動接收及回覆客人，還須另外設計持續運行的服務與渠道接駁；目前不包含 WhatsApp 或自動客服。

## 哪一部分需要重新部署

採用 [Sites 入口＋獨立原生後台](SITES_NATIVE_GATEWAY.md)時，Sites 提供登入後的入口及工具接駁，畫面、業務功能與公司資料由後台提供：

- 相容的畫面或業務程式修改：更新原後台，沿用資料與儲存；不一定重新發布 Sites。
- Sites 接駁程式或工具合約修改：先更新相容後台，再發布同一 Sites 入口並核對工具。
- 日常資料、既有設定及相容 Agent 登記：直接保存，不發布程式。

若採用資料保存在 Sites 自身的另一種架構，按其實際程式、資料庫及儲存適配更新同一 Site，完成該平台的備份及還原驗收。不能只看網站網址就判斷資料位置，也不能把 GitHub 提交或本機測試當成正式部署完成。
