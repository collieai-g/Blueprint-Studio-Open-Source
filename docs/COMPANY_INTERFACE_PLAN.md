# 公司工作台介面增補與精簡方案

[產品定位](HARNESS_ENGINEERING.md) · [現有使用方式](USER_GUIDE.md) · [開發流程](DEVELOPMENT.md) · [產品參考](https://github.com/collieai-g/Blueprint-Studio-Open-Source/blob/main/research/company-interface-reference.md)

**下一輪應讓使用者更容易處理「今天做甚麼、何時要完成、材料放在哪裡」：先整合重複入口與資料清單，再加入工作月曆和個人打卡。** 功能可以增加，但使用者需要理解的概念、必填欄位與常駐操作應減少。

本頁是介面與產品設計提案，盤點基線為 `f90c0d47fcdd93a09d70b1cc7482792b7b1259b3`。提案沒有修改正式介面、資料結構或私人工作台；Agent 執行器、模型開發及新增測試 Harness 不屬本輪設計。

## 1 現有內容與真正的缺口

| 使用需要 | 現有基礎 | 介面缺口與判斷 |
| --- | --- | --- |
| 今天要做甚麼 | 工作紀錄待辦、項目、另一類 studio task；目前待辦頁分開顯示「其他待辦」 | 先呈現一份待辦清單，來源放詳情，使用者不必先分辨資料模型 |
| 何時要完成 | 待辦到期日、項目預計完成日、工作紀錄日期 | 可先用同一批資料形成月曆；目前沒有完整月曆介面 |
| 到班及離班 | 成員的工時紀錄只有日期、分鐘、備註；工作紀錄保存成果與決定 | 這些不是實際打卡。新增打卡需保存本人、開始／結束時間及更正歷史 |
| 收集公司材料 | 原檔、網址、筆記、分類、標籤、收藏集、主題、靈感及收件匣引用 | 材料角色多於日常所需；優先把同一原始材料合成一列，減少重複整理 |
| 找回和使用材料 | 關鍵字搜尋、類型、主題、釘選、選定來源交接 | 缺少簡單一致的「收下、找回、拿來做事」動線 |
| 公司管理 | 已有客戶、報價、發票、成員等頁面，多數未常駐主導航 | 不需要一次把全部公司模組攤開；有使用需要時從相關工作進入 |

盤點依據：[導航](../library_web/navigation.js)、[待辦與文件呈現](../library_web/studio.js)、[既有欄位](../blueprint_library/studio_schema.py)、[工作紀錄](../blueprint_library/workdays.py)。既有四主入口已經簡化，舊專員和接駁設定也多已收起，不能把它們當成目前仍全面外露的問題。

## 2 日常資訊架構

四個主入口保留。下一步減少每個入口內的重複概念，用「看同一份工作或材料的不同方式」承接新增內容。

| 主入口 | 日常內容 | 偶爾使用的內容 |
| --- | --- | --- |
| 總覽 | 使用者選加入的「今日工作」卡：下一步、近期到期、自己的打卡狀態 | 自選常用引用與排版；既有使用者配置保留 |
| 工作 | 待辦、月曆、項目、紀錄 | 業務收件匣、我的打卡歷史、團隊或客戶等按需入口 |
| AI | 專業方法與交接 | Agent、工作指令及既有管理功能放「更多」；保留進行中工作的可達入口 |
| 資料 | 同一材料庫的全部、待整理、主題、常用視圖 | 已封存、分類與標籤管理、歷史及進階選項 |

「今日工作」是新增可選模組，不把現有預設空總覽改成一頁強制儀表板；概念稿展示的是使用者已選加入後的樣子。打卡入口放在今日卡，或「工作 → 更多 → 我的打卡」，不新增第五個主入口。月曆放在工作內，不另設一套導航。

頁首保留一個一致的搜尋入口。第一輪可以導向明確分組的工作／資料結果；未完成跨模型查詢前，不把現有各頁搜尋包裝成已支援全域搜尋。

## 3 應增加甚麼 同時減少甚麼

| 增加的實際用途 | 同時合併或收起的內容 | 使用者少做的事 |
| --- | --- | --- |
| 一份待辦清單，可按今天、本週、項目查看 | 「待辦／其他待辦」的兩種可見模型 | 不用先判斷應在哪一種待辦新增或完成 |
| 月曆與日期詳情 | 額外重建一份「行程待辦」的做法 | 在列表與月曆修改的都是同一筆原紀錄 |
| 我的到班／離班及歷史 | 今日頁上完整團隊工時表和人事表單 | 一個主要按鈕完成當下動作，詳情按需展開 |
| 一個收集入口，選檔案、網址或筆記 | 分散的「加入文件／新增收藏／新增靈感」決策 | 先保存材料，不用先理解它屬哪個模組 |
| 同一材料庫與待整理視圖 | 文件、收藏、靈感衍生資料各佔一列的重複感 | 一筆材料只整理一次，相關用途在詳情呈現 |
| 對外統一稱「主題」 | 收藏集與主題兩套用語、六種設計靈感分類的導航地位 | 按業務需要找資料，不用配合預設設計行業分類 |
| 統一「常用」視圖 | 原有星號收藏、頁面釘選與總覽卡片的多套術語 | 用一致操作收藏常用入口；總覽位置仍是獨立顯示偏好 |
| 明確主要動作及詳情抽屜 | 每張卡都出現轉待辦、釘選、更多 AI 操作、完整技術欄位 | 清單先讀名稱、狀態、日期，打開後再做次要操作 |

「刪減」指刪減日常介面上的重複決策，不刪原紀錄、附件、歷史、權限或舊連結。不能把本來已隱藏的舊頁面算作本輪新增精簡成果，也不能只用 CSS 隱藏舊入口而令既有工作失去操作路徑。

## 4 今日工作與個人打卡

今日卡集中顯示本人當下最需要的資訊：到班狀態、下一項工作、近期到期事項。打卡是卡片的一個簡單區塊，不把總覽變成人事管理頁。

- 尚未開始：一個「上班」按鈕。
- 已開始：顯示本次開始時間及一個「下班」按鈕。
- 已結束：顯示本日已完成時段；需要再開始工作時可建立下一段。
- 「我的紀錄」開啟本人歷史，按日或月查看；更正需保留原因與原時間。

第一版先做個人明確操作的工作時段，不加入排班、薪酬、定位、人臉或背景活動監測。顯示總時段長度，不直接稱為薪資計算的可付工時；休息、加班及公司規則日後另定。

打卡使用服務端保存的時間，顯示明確時區，跨午夜時保留原開始時間。系統按本人身份限制同一時間只能有一個未結束時段；離線或回應不明時先查回狀態，不顯示虛假的打卡成功。

現有成員人事資料受管理權限保護，不能為了員工打卡而開放整份人事紀錄。個人查詢與主管彙總分開授權。**打卡需要新的持久資料行為與本人存取範圍，不是加兩個按鈕便完成。** 現有工時分鐘和工作成果紀錄保留，不推算或回填成歷史到班時間。

## 5 月曆先呈現已有日期

第一版建議「月份＋選定日期清單」，手機以日期清單優先，月視圖可切換。到期事項、歷史紀錄及出勤有不同標記，避免把過去完成內容看成未來安排。

| 內容 | 採用日期 | 點開後的行為 |
| --- | --- | --- |
| 待辦 | 原待辦到期日 | 開同一筆待辦，完成或改日期仍更新原紀錄 |
| 項目 | 項目預計完成日 | 開原項目；不要把沒有日期的里程碑補成行程 |
| 工作紀錄 | 紀錄所屬日期 | 顯示當日成果與決定；不是會議開始時間 |
| 個人打卡（完成該功能後） | 本人時段所屬日期與時區 | 查看本人紀錄；不把團隊敏感內容混入共用月曆 |

第一輪不需要建立與上述內容平行的 calendar copies。統一呈現時保留來源類型與 ID；不同待辦模型即使 ID 相同也不混淆，完成狀態轉交原本的保存路徑。

沒有到期日的待辦仍在「未排期」清單，不從月曆消失後便找不到。只有日期的期限按全天事項呈現，不換算成半夜會議。月曆查詢先按可讀資料範圍取得日期區間，不能只把目前第一頁紀錄畫成完整月份。

真正會議、預約或假期需要各自的開始、結束、時區、參與者及權限，留到工作日期視圖穩定後再加入。第一輪不接外部 Google／Outlook Calendar，也不承諾同步或通知。若日後加入付款期限等資料，仍須按角色控制其可見內容與數量。

## 6 資料收集從資料夾思維轉向材料使用

### 先釐清目前的自動整理

本機資料夾工具依名稱、用途及已給標籤建議分類；公司材料分類也主要依格式、檔名、筆記及部分文字規則，沒有自行向模型詢問或抓取網址。小型 UTF-8 文字／程式檔可取得文字；PDF、Office、圖片、影片保留原檔，現時沒有全面 OCR／全文抽取。收藏 YouTube 連結亦不等於已取得字幕。

因此，資料夾、分類與標籤協助整理材料，但不表示系統已理解內容。現況依據：[資料夾規則](../blueprint_folders/core.py)、[公司分類](../blueprint_library/classify.py)、[檔案保存](../blueprint_library/store.py)。

### 四步收集流程

```mermaid
flowchart LR
    A[一個收集入口] --> B[先保存原材料]
    B --> C[待整理視圖]
    C --> D[補用途 可選主題]
    D --> E[以搜尋 主題 常用找回]
    E --> F[選為本次工作的材料]
```

**收下。** 使用者選檔案、貼網址或寫筆記。標題先帶入已有檔名或網址，保留原始資訊；「為甚麼留下／準備用在哪裡」以現有 notes 作可選補充。先保存，不要求立即選類別、建資料夾或填一串標籤。筆記可保存為既有文字文件或報告，不必新增另一種私人筆記資料庫。

**整理。** 同一原始 item 的收藏、靈感和收件匣引用合成一列，原引用保留在詳情。按已存在的 item ID／引用關係合併，不按相同標題盲目刪除；不同材料有相同網址或檔案時只提示核對。

**找回。** 以「全部、待整理、主題、常用」四個視圖配合搜尋；檔案、圖片、影片、網址是類型篩選，標籤放詳情或進階篩選。這些是同一材料庫的查看方式。已封存放更多選項，仍可搜尋與還原。

**拿來做事。** 勾選材料後，用一個「用於工作」動作接到指定項目或既有交接。保留原來源及版本，工作成果再連回材料。這裡只改善選材與交接的介面，不擴展 Agent 執行能力。

### 把兩種狀態講清楚

「待整理／已整理」回答使用者是否已處理這份材料；「只有網址／原檔已保存／已有可讀文字」回答目前實際保存了甚麼。兩者獨立：使用者可以確認一條網址已整理，即使尚未讀取全文；有自動標籤也不代表使用者已整理。

待整理不能永久等同「沒有收藏集」。既有未分類狀態可作初次候選，但使用者明確完成整理後，即使沒有指定主題也能離開待整理。實作時需有可保存的確認狀態，不能只在前端暫時藏起來。內容取得狀態依真正保存的文字／附件／來源證據判斷；既有 `capture_state` 主要描述截圖，不能直接充當全文理解狀態。

collection／topic 已有相同 ID 的相容橋接，介面可統一稱「主題」。舊單一收藏集歸屬保留，多個項目或工作脈絡優先用引用，不複製原檔；若未來需要真正多主題編輯，另設清楚的關係與相容方案，不假裝現有 `collection_id` 已支援多選。

工作收件匣保留真正需要處理的業務內容；材料的待整理只在資料視圖聚合，同一份新材料不再要求到工作與資料兩處各整理一次。遷移時只調整日常呈現，原收件匣項目及處理歷史仍可找回。

## 7 每張清單先少顯示 按需要展開

工作列先顯示「名稱、到期／日期、狀態」，資料列先顯示「名稱、類型、用途短句」。來源、標籤、版本、歷史與次要操作放詳情。常用主要動作保持可見，不把上班／下班、打開、完成待辦等藏進多層選單。

一個「收集」入口可在資料頁常駐，其他頁由既有操作選單進入同一表單。搜尋可導向同一結果頁，並顯示工作／資料分組；不重複建一套項目資料和月曆資料。

不要把所有新增卡片強制塞入總覽，不重設已有個人版面。公司手冊、客戶聯絡、常用品牌素材可以先放在主題和常用中；已有客戶、報價及財務頁仍按需使用，本輪不另加 CRM、完整人事或費用審批主入口。

## 8 Zendesk 值得借鏡的範圍

| 官方參考 | 對藍圖的設計運用 |
| --- | --- |
| [Views](https://support.zendesk.com/hc/en-us/articles/4408888828570-Creating-views-to-build-customized-lists-of-tickets) 以條件、欄位與排序組織同一批工作 | 今日、本週、月曆和按項目查看共同引用原紀錄 |
| [知識內容組織](https://support.zendesk.com/hc/en-us/articles/4408845897370-Organizing-knowledge-base-content-in-categories-and-sections) 保持內容層次與閱讀入口 | 先做淺層主題與搜尋，避免為空的分類多加一頁 |
| [Context panel](https://support.zendesk.com/hc/en-us/articles/4408836526362-Using-the-context-panel) 按當前工作提供相關資訊 | 日常清單簡短，打開後才看完整來源與細節 |
| [WFM time tracker](https://support.zendesk.com/hc/en-us/articles/6443354661402-Starting-and-ending-your-day-in-the-Zendesk-WFM-time-tracker) 提供開始／結束工作操作 | 借鏡簡單時段動作，先做本人紀錄；不照搬完整員工管理 |

Zendesk 的 Google Calendar 接駁屬 WFM integration，不能將其描述為所有核心工作台預設已有的日曆。藍圖先做自己的工作日期視圖；參考結論不要求購買或接入 Zendesk。

## 9 建議下一輪實作次序

| 次序 | 小範圍交付 | 使用者可見的完成標誌 |
| --- | --- | --- |
| 1 先整理資料入口 | 一個收集表單、同一材料展示、待整理與主題用語整合 | 同一材料不用重複上載或到多頁整理；標籤可選，狀態誠實 |
| 2 合併待辦並加入月曆 | 原待辦來源統一呈現、已有日期的月份與日期清單 | 列表和月曆開同一筆；未排期內容仍找得到；權限一致 |
| 3 個人打卡 | 今日卡的上班／下班、本人歷史、時區及更正 | 刷新後可讀回同一時段，不從既有工時猜時間；本人權限可用 |
| 4 視需要再擴展 | 真正會議／預約、主管彙總或跨資料搜尋 | 有明確業務需要才加，不以增加模組數作目標 |

這是建議優先級。若公司目前最急需要出勤紀錄，第 3 批可提前獨立做；它不必等待整個材料庫或完整月曆，但仍需自己的持久保存與權限。

下一個開發任務可直接定為：**「把資料收集和找回整合成一條簡單動線，保留原資料，減少重複入口」**。之後按表中邊界逐批實作。現有開發檢查沿用既有規範，本輪不新增測試 Harness 工程。

## 10 概念稿與開發交接

[可點擊概念稿](https://github.com/collieai-g/Blueprint-Studio-Open-Source/blob/main/research/company-interface-preview.html) 僅展示合成資料與互動方向；完整來源中的 `research/company-interface-preview.html` 可另存後由瀏覽器開啟。它不連接公司後台，也不保存真正打卡、工作或材料，並非已完成介面或正式截圖。

實作每批時沿用目前原始 ID、來源、完成狀態、附件、歷史、角色及版面偏好。任何「合併」先定義展示映射，再決定是否需要資料遷移；舊深層連結仍能開回原物件。資料收集、日期聚合與打卡涉及不同保存責任，不能以同一張示意畫面取代這些工作。
