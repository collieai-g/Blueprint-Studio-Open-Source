# 更新到真正可以使用

V2.5 原生服務優先使用 [NATIVE_LIFECYCLE.md](NATIVE_LIFECYCLE.md) 的內置維護流程，完成備份下載與還原後再更新。此頁保留平台接續規則；原生維護功能不代表 Sites 已有 D1／R2 備份能力。

入口回報 `deployment_mode: sites_native` 時，先按 [接駁指南](SITES_NATIVE_GATEWAY.md) 核對資料後台。公司資料使用原生備份與部署路線；Sites 只有接駁程式需要更新時才另發佈。以下 D1／R2 要求適用於資料存在 Sites 的安裝，不按網址外觀猜資料位置。

**本頁只適用於本次仍要更新原站。** 如果使用者明確改選「全新安裝、保留舊站不動」，保留舊任務記錄並轉到 [INSTALL.md 的任務選擇](INSTALL.md#先確定這次任務才讀取進度)，另用新的私人進度及服務。不要再次取回舊候選或等待舊站備份；也不能將新站完成說成原站已更新。遇到升級阻礙本身不代表取得另建空白工作台的授權。

更新的終點是：**原網址已使用新版、舊資料仍在、AI 能寫入並讀回，右側顯示同一筆結果。** 保存候選、發佈開源版本、上傳私人來源，都只是途中步驟。

使用者把 [UPDATE_AI.txt](../UPDATE_AI.txt) 貼給管理原工作台的 AI，由 AI 接續整個流程。以下步驟是 AI 的工作清單，不是要求使用者逐項操作。

開始時先做一次能力核對：能否取得私人來源、能否完整備份及還原正式資料與附件、能否發布原服務、能否驗證正式結果。優先留在已有設定生效、具備這些能力的更新對話完成。任何必要能力缺少，就早點說清楚具體缺項，同時完成不依賴它的工作；不要做完一次來源保存後，才把「仍未能部署」當作新發現。藍圖 MCP 當前未載入可以留待部署後接駁，與無法備份／部署的缺口分開。

## 一次確定目標，整段流程沿用

AI 在私人進度記錄以下資訊，不能寫入公開倉庫：

- 任務目標：完成原站更新；明確要求「只保存」就只保存，明確改為獨立新安裝則轉交安裝入口並保留舊站。
- 原網址、Site ID 或原生服務、資料與附件位置、目前正式版本的證據。
- 已保存候選的版本、私人倉庫及完整 commit；沒有候選時才建立。
- 本次選定的正式目標 tag／commit。途中不要因上游再發一版就不停更換目標。
- 已完成階段、下一步、尚缺能力，以及完整備份的私人位置與校驗紀錄。

「保留原網址及資料」不等於「不要部署」。一段只用來保存來源的子任務，也不能取代原來的升級目標。若上一段明確要求不要改正式站，完成保存後應回報「保存完成，正式更新尚未執行」，並提供繼續正式升級的完整指令。使用者要求繼續升級後，按本路線接續；不能繼續沿用子任務的停止條件，也不能無視使用者仍有效的只保存要求。

## 五個階段，完成一步就接下一步

| 階段 | AI 執行的工作 | 完成證據與下一步 |
| --- | --- | --- |
| 1. 取回及整合程式 | 核對既有私人檢查點，取回候選；按本次目標整合差異，保留原平台的登入、儲存和自訂內容 | 來源與目標一致、必要測試通過；接著補齊備份，不能停在「已保存」 |
| 2. 核對可還原備份 | 保存原來源與正式部署版本、完整資料庫、全部附件、必要設定及瀏覽器排版；暫停寫入或使用平台一致快照 | 私人備份可讀取、內容與數量核對、還原方法明確；接著更新原站 |
| 3. 更新原正式服務 | 保留原 Site ID／服務、網址、存取權、資料庫與附件綁定；提交、保存版本及部署 | 平台回報成功、確切部署 ID 與原網址；接著驗證真正使用中的版本 |
| 4. 核對右側畫面及舊資料 | 讀正式後台版本與介面資產，確認登入、舊紀錄、待辦、歷史、附件與排版；開啟同一網址 | 正式站版本及內容相符；接著驗證 AI 工具，不只截圖或看版本標籤 |
| 5. 接通 AI 並完成一項工作 | 載入原站的新版工具，使用接駁中心的實際參數寫入、讀回，再由畫面確認相同紀錄 | 回報同一紀錄 ID、原網址、確切版本及資料保留結果，才可稱「更新完成」 |

來源整合與不會改正式資料的測試，可在處理備份能力時繼續；正式部署必須等必要備份完成。階段 3 成功後若階段 5 受阻，應說「網站已更新，AI 接駁未完成」，不能把它重新稱為「尚未部署」，也不能因此自動回復網站。

## 不要把幾種版本混在一起

- **公開正式版本**：開源 release 的 tag 與 commit，是本次整合的目標。
- **私人候選版本**：待部署程式的實際版本。使用新版保存工具，不會改變候選版本。
- **正式網站版本**：原網址實際運行的程式與介面版本。需讀正式服務，不能由候選推斷。
- **Sites 版本序號**：平台的第 1、2、3 次保存，並非產品版本。

例如候選是 2.4.0、目標是 2.4.2：先整合差異並重新測試，再部署一次 2.4.2。不必先部署 2.4.0 再升級，也不能只改版本文字。私人 GitHub 的檢查點 commit 用來取回來源，**不能直接充當 Sites 來源倉庫的發佈 commit**。

## 兩條實際部署路線

### 本機或原生雲端

沿用原服務與私人資料路徑，按 [UPGRADE.md](UPGRADE.md) 停止寫入、保存一致備份、驗證備份，再整合目標程式，啟動或重新部署原服務。從實際入口驗證版本與舊資料，最後接通原後台的 MCP。AI 執行環境內的新資料庫，不能代替使用者原本的資料。

### 已使用 Sites 的工作台

1. 讀目前 Sites 技能、原 Site、已保存版本和目前可用的發佈工具；保留原存取權。既有私人檢查點成功取回後，不再要求使用者搬 ZIP。
2. 透過 Sites 支援的來源流程開啟**同一 Site**，從原平台取得部署設定。檢查點不含 `.openai` 設定，不能因此另建網站或猜資料綁定。
3. 將已核對的候選工作樹整合到原站來源，保持已套用的遷移檔不變，按目標版本更新 UI、後台 API 與 MCP。UI 包本身不是完整 Sites 後台。
4. 補齊原資料庫、R2 物件與必要設定備份，安排一致的資料保留比對。通過後，以官方來源流程提交／推送並打包同一份已測試程式。
5. 用平台回傳的 Sites commit 與完整封包保存版本，再按原受眾部署到原 Site。若現有結果已建立部署，接續該部署，不重複新建。私人站使用私人部署操作。
6. 部署成功後核對正式 API 與介面；打開同一網址。只有確認正式資產是新版、畫面仍舊時，才處理一般重新載入或 service worker 快取。不要叫使用者清除所有網站資料，否則可能丟失私人排版。

## 三種常見卡點的處理

**完整附件備份缺少。** 空資料表、附件清單或一般 JSON 匯出，均不能證明 R2 已完整備份。AI 要核對完整物件清單、分頁是否結束、每個物件內容與校驗碼；確實為空亦需來自物件儲存的完整列舉證據。平台若只提供讀資料表、未提供 R2 列舉／下載／可還原快照，應明確列出缺少的能力與已查過的支援途徑。不要只說「請完成備份」，更不能以先做有資料遷移的升級來取得備份功能。只有確實存在的管理入口才能指示使用者操作；不存在就如實回報功能缺口，保留候選並繼續其他可做工作。

**藍圖工具未載入。** 發佈網站所用的 Sites 工具，與部署後供 AI 寫資料的藍圖 MCP 工具，是兩組能力。舊正式版缺少新版藍圖工具時，先完成必要備份及網站更新，再刷新／授權及載入工具；不能要求舊版先具備新工具，形成無法前進的循環。也不能把直接 HTTP 寫入當作目前對話的外掛驗收。登入或工具選擇需使用者操作時，給一個確切動作後接續。

**網絡或環境不符。** 使用目前對話的實際環境觀察。另一個對話網絡恢復，不代表這個執行環境也已套用。先使用可用的官方連接工具；若確需切換，選已有設定生效且具備備份／部署能力的環境，帶入私人來源位置與原更新目標。不要反覆叫使用者加入同一網域，不繞過代理、登入或存取限制。

## 停下時必須留下可執行的下一步

AI 每次回報包括：已完成哪一階段、正式站是否已改動、下一步要做甚麼，以及哪項能力確實缺少。已經完成且輸入未變的工作直接沿用；不能把「來源已保存」當成整個任務完成，亦不能要求使用者自己設計後續流程。

私人進度可以使用以下簡單欄位：`goal`、`target_release`、`site_identity`、`candidate`、`backup_evidence`、`deployment`、`live_verification`、`ai_verification`、`next_action`。這些是 AI 維護的工作記錄，不是要求使用者填寫的表單，也不能靠手工填 `true` 代替工具證據。
